# Architecture

## Implemented foundation

A modular monorepo with Laravel 12 / PHP 8.3 in `apps/api` and React / TypeScript / Vite in `apps/web`. Dependencies are resolved in Composer and npm lockfiles. Nginx serves the compiled SPA and proxies `/api`, `/sanctum`, and `/up` to PHP-FPM on one origin. React Router controls navigation; TanStack Query owns server state; Tailwind provides styling.

PostgreSQL 17 stores durable records; the foundation migration enables pgvector. Redis stores sessions, cache and throttles. Phase 2 chat jobs use the PostgreSQL database queue for atomic submission; other future queues may use Redis. API, queue worker and scheduler share an image. Internal Docker networking exposes only Nginx on loopback port 8080. Only the chat and summary workers also join an egress network to reach OpenAI; PostgreSQL, Redis and the API remain on the private backend network. Named volumes persist PostgreSQL, Redis and Laravel storage. No GPU is required.

## Authentication and authorization

The SPA obtains `/sanctum/csrf-cookie` and sends the decoded XSRF token in mutation headers. Sanctum stateful middleware uses encrypted HttpOnly session cookies; login rotates the session, logout invalidates it. Browser sessions require an allowed Origin/Referer. Public auth is limited to five requests per minute per IP, and APIs to 120 per user/IP. Passwords are hashed; password fields are hidden from serialization. API failures use Laravel JSON `message` and optional validation `errors`.

Registration atomically creates a user, an organization and owner membership. Phase 1 supports listing the user's organizations, not organization administration or invitations. A project creator becomes its initial project member. All project listings and reads require organization AND project membership; `ProjectPolicy` governs individual resources. Only organization owners with project membership can update, archive, restore or delete. Client input cannot reassign a project's organization. Deletion cascades project membership. UI confirmation precedes deletion.

## Data model

Users, organizations and projects have UUID primary keys. Membership pivots use composite primary keys and cascading foreign keys. Projects store name, nullable description, cloud-processing permission (false by default), archive timestamp and timestamps. Organization/creation-time indexes support scoped pagination (20 items per page). Laravel's sessions, cache, queue and Sanctum infrastructure tables are included. Successful API mutations record actor, route template, optional project reference and timestamp in an audit ledger within the mutation transaction; request bodies, passwords and session tokens are never recorded. Remaining master-specification tables belong to their owning phases.

## Future boundaries (unimplemented)

`services/intelligence` now implements private CPU embeddings with FastAPI. Repository parsing/Tree-sitter are now implemented in Phase 4; model-aware chat token budgeting remains Phase 5. `extensions/vscode` is reserved for the Phase 7 client. The VS Code extension remains unimplemented. Laravel now owns the LLMProvider interface and OpenAI adapter. Routing, model-aware ContextBuilder, verification and spending ledgers remain future phases. Python must not duplicate these rules. Ollama and additional cloud adapters are deferred until their approved phases.

Embeddings record model identifier, version, dimensions, pooling strategy and artifact/runtime fingerprint. A model change requires a new index generation and explicit reindexing; incompatible vector spaces are excluded before ranking. Retrieval filters by authorized project and owner before ranking.

## Operational limits

This is a local foundation, not a production release. TLS, production secret provisioning, backups, observability, retention administration and security/performance acceptance remain Phase 8. Cloud AI calls can transmit submitted prompts, bounded completed turns and selected private memory only when project cloud processing is enabled. Explicit summary generation has the same cloud gate. Repository access is explicitly mounted read-only; there is no code execution, tool calling or automatic file modification. See decisions and progress for exact verification evidence and limitations.

Implementation references: [Sanctum](https://laravel.com/docs/12.x/sanctum), [Vite setup](https://vite.dev/guide/).

## Phase 2 chat

Conversations are private to their creator and require current organization AND project membership. Project owners alone change project cloud permissions; authorized members may manage their own conversations. Shared-project membership does not expose another user's conversations.

`conversations`, `messages`, and `message_events` add UUID resources, ordered turns, unique request keys, reply relationships, attempt/status fields and persisted SSE events. Message-event integer IDs are cursors, not public resource identifiers. Each request locks the conversation, validates policy/privacy/configuration/input limits, inserts one prompt and one assistant, and enqueues a database job inside the same transaction (including the audit middleware transaction). This avoids a committed prompt with a lost Redis dispatch. The database queue must use the same database connection as the application. Conversation deletion takes the same lock and refuses active work.

A worker atomically claims `queued → streaming`, rechecks access/privacy, sends only completed pairs and the current prompt, then stores each delta and event together. Completion stores sanitized token usage and provider response ID. It never marks code verified. Responses use a fixed HTTPS OpenAI endpoint, `store: false`, no tools, bounded HTTP timeouts, safe errors and no automatic paid retry/fallback. API keys are read only from server configuration. Model identifier, context metadata, pricing and output limit are configurable; no model name or price is hardcoded.

A UUID idempotency key replays the original response for matching input and rejects changed input. Only one response runs per conversation. Manual retry references the failed attempt number; duplicates return the newer attempt without another job. At most three attempts are allowed, and only the latest response may be retried. Stale/duplicate jobs cannot claim a newer attempt. Each stream serves only the bound message's current attempt, supports Last-Event-ID (or `after`), rechecks membership per poll, and closes after a bounded window so EventSource reconnects without sending the prompt again. Nginx buffering is disabled. Its variable FastCGI upstream uses Docker DNS with a five-second cache so recreating the API container does not leave a stale address ([Nginx reference](https://nginx.org/en/docs/http/ngx_http_fastcgi_module.html#fastcgi_pass)). Browser disconnects do not cancel durable jobs.

Worker timeout is 150 seconds, database queue visibility 210 seconds. Every minute `chat:recover` marks queued/streaming work older than 300 seconds failed, preserving partial output and requiring explicit retry. This also handles a worker lost before acknowledging a cloud response. A retry can incur another provider charge; the app does not claim exactly-once external inference.

Phase 2 uses conservative character and turn limits (default 24,000 input characters, 20 prompts, 1,024 output tokens), rejects excess input instead of truncating code, and keeps failed turns out of future model context. These are bounded foundation controls, not model-aware token optimization or financial budgets. Those features belong to Phase 5. Provider context-window errors are surfaced safely. Stored message content remains plain text; Prism renders fenced code through React tokens, with no raw HTML execution.

Provider implementation follows the [official OpenAI streaming guide](https://developers.openai.com/api/docs/guides/streaming-responses) and [streaming event reference](https://developers.openai.com/api/reference/resources/responses/streaming-events). `store: false` disables response storage for later API retrieval; provider retention policy still applies. Tests mock external inference; no live credential/paid-model verification is claimed.

## Optional host database access

The owner requested access from a database client outside Docker after Phase 2. `infrastructure/compose.database-access.yaml` optionally publishes PostgreSQL on `127.0.0.1:${DB_FORWARD_PORT:-5432}`. The default Compose file retains private database networking; remote clients require an explicit port forward or tunnel. This is a configuration follow-up, not authorization for Phase 3.

## Phase 3 persistent memory

`memories` stores four categories (conversation/project/error/solution), source provenance, content hash, UUID ownership/project links, optional Git reference, immutable source links, timestamps, revision, active/invalidated state and index state. All records are **unverified**, enforced by the schema and application input whitelist. A solution-category memory is not a verified solution cache. Creator ownership plus current organization/project membership protects every record; shared-project members cannot read each other's private conversation memory. Manual correction records actor, previous hash, revision and time without overwriting original source references.

Successful chat completion atomically captures a full user/assistant pair and queues a local embedding job; source keys make capture idempotent. Existing conversations can be backfilled explicitly with `memory:reindex --capture`. Original text is preserved. Invalidating/correcting a record removes its previous embedding; deleting a conversation or memory cascades its derived records. Reindexing never resurrects invalidated sources.

`IndexMemory` claims a revision and random index token, checks current access, calls the internal EmbeddingProvider and rechecks access/revision/token under lock before publishing. Correction, invalidation, deletion or a newer job makes the old result unusable. The PostgreSQL database queue remains a transactional outbox. `memory:recover` marks work older than five minutes failed; explicit reindex retries local work. A dedicated memory worker waits for intelligence health. Chat and API requests can continue with explicit keyword fallback when vector generation is unavailable.

### Local intelligence and vector generations

The FastAPI service has no published port and no runtime egress. It accepts bounded text only through a constant-time shared-token check. It cannot authorize projects, execute commands or persist memories. Phase 4 adds constrained, read-only repository access as described below. Its responses expose only vectors and model metadata to Laravel. The default is FastEmbed with the CPU ONNX BAAI/bge-small-en-v1.5 model, 384 dimensions. Python dependencies are fully version-locked. The public Qdrant model snapshot is pinned to `aa8f8b060edb00e03bfdd08813a2949946c8ba55` and downloaded at image build, not while processing project text. A manifest rejects a mismatched runtime model/revision. The service runs as a non-root user with Hugging Face offline mode and ONNX telemetry disabled.

Every Unicode character is preserved in bounded UTF-8 segments (384 bytes). The real model tokenizer measures each segment with truncation disabled; an excessive token count fails instead of silently discarding code. Length-weighted mean pooling of segment embeddings followed by normalization gives one vector per record, using all segments. This is deliberately simple document embedding; dedicated repository/symbol chunking is Phase 4. Long records can have diluted relevance; this is not a retrieval-quality guarantee for all code/languages. The default model is English-focused and its relevance was checked with synthetic English debugging examples.

`memory_embeddings` stores revision, dimensions, model/version, pooling and an artifact/library fingerprint. PostgreSQL stores an untyped `vector` plus a dimension CHECK, allowing future generations with different dimensions. Exact cosine search filters compatible profiles and revisions and uses a CASE guard so the planner cannot evaluate distance on incompatible dimensions. Index publication replaces vector and metadata within one transaction, including dimension changes. No mixed-space ANN index is used. A SHA-256 profile includes model, version, dimensions, fingerprint and pooling. It changes when model artifacts or relevant runtime libraries change. SQLite tests use JSON vectors/cosine as a test/local fallback; PostgreSQL tests exercise the real vector operator and full-text index.

To change embedding models: configure the supported model, immutable snapshot revision, model version and dimensions; rebuild/recreate intelligence and Laravel services; run `memory:reindex`. Search compares only new compatible vectors, with keyword search remaining available during rebuild. There is no silent comparison of old/new spaces or automatic generation cutover represented as model training. Reindexing is retrieval maintenance, not fine-tuning.

### Retrieval and summaries

MemorySearch combines PostgreSQL `websearch_to_tsquery`/GIN full-text ranking, compatible pgvector cosine candidates and exact error signatures through reciprocal rank fusion. It filters private active records before searching, deduplicates content/conversation sources and refetches current revisions before returning hits. Missing embeddings produce lexical mode; embedding errors explicitly report `degraded: true`. Phase 4 adds a separate project-shared source/symbol retrieval service. Exact vector search and bounded candidate lists prioritize correctness; large-scale ANN/performance work remains Phase 8.

MemoryContext adds relevant records from other conversations/manual project memories to chat as explicitly **untrusted, unverified JSON data**, with source UUID/revision metadata saved on the assistant message. It selects whole records within a small character allowance and the existing chat input limit; it never silently slices code. It excludes the current conversation to avoid duplicating history. This narrow retrieval step is not the model-aware ContextBuilder/optimization milestone in Phase 5. UI links show the actual selected memory IDs even if the model's prose citations are imperfect.

Summaries are explicit requests, never hidden paid background calls. A `conversation_summaries` snapshot identifies the last completed assistant sequence, model, attempt, status, usage and timestamps. Identical snapshot requests return the same job/result. The worker rechecks current access, cloud permission and configuration before inference and before committing. Only completed turns are included; oversized source/output fails with no truncation. A ready summary becomes another unverified, provenance-linked memory and receives a local embedding. Paid retries are explicit and limited to three attempts; interruptions are not automatically replayed. New messages do not mutate an earlier summary snapshot. Summaries can therefore be retrieved by later private conversations.

Sources: [FastEmbed documentation](https://qdrant.tech/documentation/embeddings/fastembed/), [FastEmbed TextEmbedding source](https://github.com/qdrant/fastembed/blob/main/fastembed/text/text_embedding.py). No cloud embeddings, repository intelligence, verified fixes or fine-tuning are implemented in Phase 3.

## Phase 4 repository intelligence

See [ADR 0004](decisions/0004-read-only-repositories.md). Laravel owns association, authorization, indexing jobs, atomic publication and retrieval; Python owns bounded discovery, hashing, framework/language detection and Tree-sitter chunking. The internal snapshot API requires the existing shared bearer token and accepts a project UUID supplied from Laravel's authorized repository record. Source mounts exist only on the intelligence container, never PHP/React. An optional Compose override maps a dedicated administrator-selected host directory read-only to `/repositories`; source must be provisioned under `/repositories/<project UUID>/<registered path>`. Cross-project paths cannot escape their UUID directory. No URL cloning, Git commands/hooks, credential access, repository code execution or automatic edits occur.

Python opens paths descriptor-relative with `O_NOFOLLOW`, rejects symlinked path/Git metadata components and skips symlink entries. Git HEAD (loose/detached/packed references) records provenance; external Git worktrees/submodules are rejected. The indexed bytes are the current workspace, including uncommitted edits; SHA-256 content hashes distinguish them from Git HEAD. A HEAD change during discovery fails the scan. This is not a filesystem-wide point-in-time snapshot: concurrent uncommitted edits can produce a mixed-time workspace; use a stable sanitized checkout when exact reproducibility matters.

Hidden files/directories, known dependency/generated directories, credential-like filenames, non-allowlisted extensions, binaries/invalid UTF-8, minified files and obvious embedded credential patterns are excluded. Supported text extensions are defined in `app/repository.py`. Supported grammars are Python, JavaScript/JSX, TypeScript/TSX and PHP. Others are labeled `text`, without claiming symbol support. Framework detection recognizes manifest dependency names for Laravel, React, Next.js, FastAPI and Django; it is a heuristic, not runtime/version verification. All source text and whitespace are preserved in chunk order. Symbol boundaries and line references come from Tree-sitter; symbols longer than 3,000 characters are explicitly split, not silently truncated. Parser generation includes algorithm and pinned runtime/grammar versions.

Hard bounds: 128 KiB per eligible file, 200 eligible files, 1 MiB decoded source bytes, 500 chunks, depth 20 and 10,000 traversed directory entries. Limits fail the scan and retain prior storage; they do not silently publish an incomplete inventory. Secret-pattern matches intentionally omit the file. Mount only trusted, sanitized checkouts: these filters cannot guarantee detection of every embedded secret. Nothing in an indexed source block can authorize tools or override policy. Local-only retrieval is available regardless of the project's cloud setting; transmission in chat retains the existing cloud-permission gate.

`repositories`, `repository_files`, `code_chunks` and `indexing_jobs` are additive UUID/foreign-key tables. Registration and queueing require project configuration rights; members can inspect/search shared project source. Unlike repository source, memories/conversations remain creator-private. API discovery/status/files/inspection/search queries enforce current project and organization membership; unscoped chunk IDs never bypass that policy. Configuration mutations use audit transactions. A dedicated private `repository-worker` consumes the database queue, with no egress network or source mount.

One active job per repository is serialized by the repository lock. The worker claims its UUID once, checks owner membership/archive status, fetches a bounded snapshot and probes the current embedding profile. Compatible hashes plus parser/profile preserve existing file/chunk IDs and avoid re-embedding source. Changed files/generations prepare new embeddings outside the publication transaction. Under repository/job locks, the worker rechecks status, membership and archive state, replaces changed chunks, removes absent files (cascading chunks), then updates revision/metadata/job stats in one commit. Deletion, timeout recovery or revoked access prevents stale publication. A failed scan/inference leaves the complete last published snapshot usable. `repositories:recover` marks jobs older than five minutes failed; an explicit index request retries. Worker timeout is 150 seconds; existing database visibility remains 210 seconds. Large repositories may hit limits/timeouts and need a smaller dedicated checkout; scalable resumable staging is not claimed.

CodeSearch uses authorized project joins, PostgreSQL GIN full-text and exact symbol candidates plus compatible pgvector cosine, then reciprocal rank fusion and content deduplication. SQL CASE guards prevent incompatible dimension evaluation; SQLite tests use JSON cosine as in memory. Search rechecks membership and published revision/hash before returning references. Vectors/tokens are hidden from browser responses. Indexing a new profile is explicit; old incompatible vectors are excluded while lexical results remain useful. Matching generation-provider changes do not require embeddings to change.

CodeContext selects whole chunks within up to 6,000 remaining characters after history/prompt/memory, labels JSON blocks untrusted and persists UUID/path/lines/Git/hash references on the response. It does not implement the model-aware Phase 5 ContextBuilder. React Project Explorer handles registration/indexing/status/files/detection/search/source inspection; chat links the selected source IDs. Updated/deleted file IDs expire, returning 404 rather than substituting current text for an old citation. A repository is not a verified fix; no source is marked verified and no automated execution is added.

Tree-sitter API reference: [official Python bindings](https://github.com/tree-sitter/py-tree-sitter). Individual grammars and runtime are pinned in the intelligence requirements lock.
